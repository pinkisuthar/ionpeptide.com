*** Idem Payment Changelog ***

2026.09.16 - version 4.9.0
* New: the size of the payment method logo shown at checkout can now be set from the plugin settings (WooCommerce > Settings > Payments > Idem Payment > Checkout appearance > Logo height). Until now the size was decided by your theme, which often made the logo too small or too large. Enter a height in pixels, the width follows automatically; leave the field empty to keep your theme's default. Works on both the classic and the block checkout.

2026.08.07 - version 4.8.5
* Fix: a DECLINED renewal payment now reliably puts the subscription on hold. Two separate problems could stop that from happening. First, the "a renewal never acts on the original order" rule was applied to every notification, including declines, which silenced the suspension entirely; declined notifications are now let through to it, while every other kind — payments, refunds, and any status we do not explicitly recognise as a decline — stays covered by the rule. Second — and this one predates the previous release — the subscription behind a renewal order was looked up in a way that never finds it, so a redelivered decline suspended nothing.
* Fix: a decline on a subscription whose amount was changed after the fact no longer goes unnoticed. The amount check compared the subscription total against the ORIGINAL order's total whenever no renewal order existed yet — which differs legitimately as soon as you change a subscription's amount — and the resulting mismatch stopped the suspension from running.
* Fix: when a renewal payment is declined and no subscription can be found (WooCommerce Subscriptions inactive, or the link missing), the original order is no longer marked "failed". A later period being declined must never fail the order that created the subscription; the payment is recorded in a note instead.
* Fix: a redelivered renewal notification is recognised as already processed based on whether the renewal was ever PAID, not on its current status. On a store configured to leave paid orders "on hold" — a supported setting — a redelivery could otherwise re-run the whole payment path on an already-paid renewal: notes, payment identifiers, subscription reactivation and payment date. Renewals genuinely awaiting payment are still paid by the next cycle payment.

2026.08.07 - version 4.8.4
* Fix: a subscription renewal payment can no longer act on the order that created the subscription. When no renewal order can be found or created for it — because renewal creation failed, or because WooCommerce Subscriptions is not active — the notification is now acknowledged and the order is left untouched, with a note recording the payment so you can reconcile it on the platform. This also covers refunds: a refund on a renewal used to be applied to the original order, refunding the wrong one.
* Fix: a redelivery of a renewal payment notification no longer adds a duplicate note to the renewal order. The order state itself was never affected.
* Fix: a renewal payment notification received while WooCommerce Subscriptions is inactive no longer causes a PHP fatal error.
* Fix (security): payment notifications are checked for a valid structure before anything else reads them. A malformed notification is now refused up front instead of being processed with missing values — this matters most on stores that have signature verification turned off.

2026.08.06 - version 4.8.3
This release prepares the plugin for a platform change: subscription renewal payments are about to carry the key of the order that started the subscription. Until now they carried none, so none of the checks below applied to a renewal. Both items are therefore hardening ahead of that change, not fixes for something you have been experiencing.
* Hardening: the order-key check is now correct for renewals. It compares against the order the payment was created for, so any renewal notification — a redelivery of the payment, or a later refund on it — is accepted by that check, whereas the previous logic would have compared against the renewal order and refused it as a session mismatch once renewals start carrying a key.
* Hardening: the backup check against our API now ignores renewal payments outright. A renewal carries the original order's reference, so once renewals carry that order's key too, an original order left "pending payment" could otherwise be completed by a later renewal's payment whenever the two amounts matched — the normal case for a fixed-price subscription.

2026.08.05 - version 4.8.2
* Fix: payment notifications (IPN) are authenticated against the exact amounts signed when the payment form was generated (multi-tab safe), with strict currency validation and exact comparison at currency precision (no more 1-cent tolerance in payment decisions).
* Fix: a captured payment that no longer matches the current order total places the order on hold with a note showing the paid amount, the signed amount and the current total — instead of silently staying "pending payment" until it gets cancelled. All amounts are always written to the WooCommerce logs.
* Fix: the same protection now covers a captured payment whose currency does not match the order, and a payment whose amount matches none of the signed amounts: the order is placed on hold instead of being left "pending payment" and cancelled by the unpaid-order cleanup. This applies both to notifications and to the backup check against our API.
* Fix: the backup check against our API only completes an order when the payment carries this store's own order key, is marked completed, and matches the current total exactly. Any correlated completed payment that cannot be safely applied is placed on hold for review; payments that are not this order's, or not completed, are simply ignored. Previously a completed-looking payment could be applied without that verification, and a refunded or still-pending payment with a matching amount could complete an order.
* Fix: WooCommerce no longer cancels an order whose payment we can still find. The last-chance check that runs during the "unpaid orders" cleanup was attached to a WooCommerce event that never fires, so it never ran: past the first 15 minutes, a paid order whose notification never arrived could be cancelled. It is now attached to the event WooCommerce actually uses, and keeps the order alive when a payment is found.
* Fix (security): the order-key correlation is now validated BEFORE any order change; an IPN with a wrong key can no longer complete an order or trigger a refund.
* Fix: the subscription-renewal amount check now finds the subscription behind a renewal order (it previously looked only at parent orders and found none), so a renewal whose total was changed after the charge was scheduled is reported as a total mismatch instead of an amount mismatch.
* Fix: a failed automatic refund now answers an error to the platform instead of "ok".
* Fix: payment-link references (e.g. "12345.1") are refused with a distinct "reference-not-an-order" code instead of being mistaken for a store order.
* Fix: IPN response codes are now stable machine codes, no longer affected by the site language.
* New: an audit note is added when a second, different payment is received for an already-paid order (possible duplicate charge).
